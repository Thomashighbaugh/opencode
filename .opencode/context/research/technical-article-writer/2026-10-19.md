# Technical Article Writer — skill digest

Source: `~/Downloads/technical-article-writer` (samber/cc-skills v1.3.2, MIT). A Claude-oriented skill
for writing long-form developer content: tutorials, explainers, benchmarks, bug hunts, postmortems,
"we rewrote it in X" posts. Ships with two reference files (article structures, hooks/titles) and an
evals.json of 11+ behavioral assertions.

## The skill's own model

Phase-gated workflow — the skill refuses to draft before an intake interview:

1. **Idea sharpening** — topic, objective (single primary CTA), audience, content type, length,
   one-sentence thesis. Idea quality filters: Julia Evans ("write from what you struggled with, not
   what you mastered") and Julian Shapiro's novelty filter (counter-intuitive / counter-narrative /
   shock-and-awe / elegant articulation / makes-you-feel-seen).
2. **Title generation** — 10 variants from the 10 hook types (credibility, fear, curiosity,
   counter-narrative, eloquence, faces, value, surprise, celebration, identity). Developer
   constraints: 7–12 words, specificity over cleverness, numbers signal rigor, no superlatives.
3. **Hook + intro** — hook, stakes, promise; answers three objections (untrustworthy / irrelevant /
   implausible). Anti-patterns: dictionary-definition openers, "In today's fast-paced world…",
   "Have you ever wondered…", buried lede, roadmap-paragraph intros.
4. **Body structure** — one idea per section; show-then-tell; progressive disclosure; every section
   earns the next. Code: <20-line snippets, before/after, annotate non-obvious lines.
5. **Draft** — conclusion is implication / open question / CTA, never a restatement. Then a CTA
   pass, then a humanize pass (which must preserve the engineered hook and title).
6. **Images** — 1–3 suggestions with placement, purpose, description; optional Midjourney prompts.
7. **Title finalization** — revisit titles after the draft exists; the real focus emerges in writing.

## The skill's 8 content-type templates (medium length, 1500–2500 words)

| Type | Spine | Signature technique |
|------|-------|---------------------|
| The Bug Hunt | symptom → first hypothesis → investigation (dead ends shown) → revelation → fix → lesson | Tension via plausible-but-wrong hypotheses |
| We Rewrote It in X | pain → choice criteria → migration process → what went wrong → metrics → would we do it again | "What went wrong" is what makes it credible; without it it's a press release |
| How We Built It | what/why → constraints → architecture → key decisions as tradeoffs → what we'd change → takeaways | Frame decisions as tradeoffs, not "the right answer" |
| Lessons Learned | context → 3–5 lessons (each with a specific story) → meta-lesson | Best lesson first; story per lesson |
| Thoughts on Trends | observation → evidence → steelman → thesis → implications | The steelman separates analysis from hot takes |
| Benchmark / Data-Driven | question → methodology → results → analysis+caveats → recommendations → reproduction notes | Lead with methodology — no trust in setup, no trust in conclusions |
| Tutorial / How-To | end result → prerequisites → numbered steps (action/code/expected result/common errors) → verification → next steps | Test from scratch on a clean environment |
| Explainer / Deep Dive | why it matters → simple mental model → going deeper → common misconceptions → practical implications | Start with the simplest accurate model, then complicate it |

Plus Diataxis as a diagnostic (tutorial / how-to / explanation / reference; mixing types is the
common failure), structural anti-patterns (buried lede, kitchen sink, wall of code, false
conclusion, monotone pacing), and transition techniques (forward reference, question, contrast,
escalation — never "now let's talk about…").

# Beyond the 8 types: the fuller taxonomy of technical writing in CS/software

The skill's enumeration is a good blog-post core but undersells what technical writing actually is
in the wild. What follows is a broader map — the forms this writing actually takes, grouped by the
job the piece does for its reader. Use it to recognize a piece's true type before reaching for a
template; most real articles are one dominant type plus one or two supporting modes.

## 1. Practice-transfer writing (reader leaves able to *do* something)

- **Tutorial** (learning-oriented, Diataxis): guided path to a working end state.
- **How-to / recipe** (task-oriented): solve one specific problem; assumes competence, skips theory.
- **Cookbook / pattern catalog entry**: named problem → solution sketch → when it fails. (Go
  cookbook style, "small patterns" posts.)
- **Setup / environment guide**: getting from zero to a working toolchain; dies fast, dates fast,
  still the most-searched genre on the internet.
- **Migration guide / upgrade walkthrough**: version-to-version moves, breaking-change navigation.
- **Debugging walkthrough / bug hunt**: the skill's Bug Hunt; also its shorter cousin the
  **"the bug was X" micro-post** (one symptom, one root cause, one lesson — Julia Evans / danluu
  style).
- **Performance deep dive / optimization journey**: profile → hypothesis → fix → measure; half
  benchmark, half bug hunt.

## 2. Knowledge-transfer writing (reader leaves *understanding* something)

- **Explainer / conceptual deep dive**: the skill's Explainer. "How does X actually work?"
- **Internals / under-the-hood series**: "How Postgres stores a row", "What the JVM does with your
  lambda." Reader can't act on it directly; it changes how they reason.
- **"X from scratch" build-along**: write a database / OS / regex engine / compiler in Y. Teaching
  by reconstruction — the reader builds the thing to understand the thing.
- **Paper explainer / distillation**: academic result translated to practitioner language.
- **Concept history / "where did X come from"**: why the technology is the way it is (why CSS is
  like that, why Git's UI is like that). Often the highest-traffic explainers.
- **Glossary / reference-adjacent essay**: "Everything you need to know about X, briefly" — sits
  between docs and blog; Diataxis says reference rarely works as a blog post, but the
  essay-shaped reference ("X explained in one page") is a real and durable form.
- **Comparison / "X vs Y" explainer**: conceptual contrast (processes vs threads vs actors), not a
  benchmark — the reader wants a decision frame, not numbers.

## 3. Experience-transfer writing (reader inherits your *judgment*)

- **Postmortem / incident writeup**: the genre with the strongest conventions in the industry
  (timeline, impact, root cause, what worked, action items). Public postmortems (Cloudflare,
  GitHub, Stripe) are a distinct literary form.
- **Lessons learned / retrospective**: the skill's template. Includes **"N years of X"** posts
  ("10 years of running Postgres in production").
- **How We Built It / engineering blog post**: the skill's template; the backbone of every company
  engineering blog (Netflix, Uber, Shopify, Discord).
- **We Rewrote It in X / migration story**: the skill's template.
- **Failed-experiment writeup**: "we tried X and rolled it back." Rarest and most trusted; the
  counter-narrative filter almost always passes.
- **Trade study / decision record made public**: an ADR written for strangers — options, criteria,
  choice, regrets.
- **War story / anecdote**: single incident, told for the principle. Cheaper than a postmortem,
  often more memorable.

## 4. Opinion & industry writing (reader updates their *position*)

- **Essay / opinion piece**: the skill's Thoughts on Trends; steelman required.
- **Rant / polemic**: legitimate form when it's honest ("X considered harmful" lineage). Needs the
  steelman even more than the essay does.
- **Tech-strategy analysis**: what a company's move means (Stratechery-shaped); written by
  engineers, it becomes "what this acquisition/API deprecation means for your stack."
- **Trend report / state-of-X survey**: Stack Overflow survey writeups, ThoughtWorks Radar, "State
  of JS" commentary. Data-driven opinion.
- **Prediction / year-in-review**: low-trust genre unless it keeps score on last year's predictions.
- **Response / rebuttal piece**: "a response to [viral post]." High engagement, high burn risk.

## 5. Tool & product writing (reader *evaluates or adopts*)

- **Release notes / changelog**: the most-read technical writing most engineers ever write. Good
  ones are a craft (keep-a-changelog conventions, "why" per change).
- **Launch post / announcement**: celebration hook + what it is + why + how to try it.
- **Tool review / "I tried X so you don't have to"**: hands-on evaluation with a verdict.
- **Benchmark / shootout**: the skill's template. Methodology first.
- **Comparison matrix / buyer's-guide-for-engineers**: feature tables plus a decision frame.

## 6. Community & career writing (reader relates)

- **Career narrative**: "how I became a staff engineer", job-hunt retrospectives, salary
  transparency posts.
- **Mentorship/advice essay**: "advice to my younger self", "what seniority actually means."
- **Community meta-writing**: how a community/team/venue works; conference talk recaps;
  meetup summaries.
- **Reading list / annotated bibliography**: curated links with the curation as the value.
- **Week-in-review / link log**: the newsletter-shaped form (deliberately out of scope for this
  skill, but a major genre — Changelog Weekly, Golang Weekly).

## 7. Formal & semi-formal written genres (the "writing that isn't a blog post" tier)

- **Reference documentation**: API docs, man pages. Diataxis reference quadrant.
- **Concept documentation / architecture overview**: docs-site explainers.
- **Style guides and conventions docs**: "how we write Go at X."
- **RFC / design doc / tech spec**: internal by default, but the public ones (IETF RFCs, Python
  PEPs, Rust RFCs) are among the most influential technical writing in existence.
- **Whitepaper**: marketing-adjacent now, but the systems whitepaper (Dynamo, MapReduce, Bitcoin)
  is the genre that built the industry.
- **Academic paper / technical report**: the upstream source the blog ecosystem distills.
- **Runbook / playbook**: operational writing; almost never public, increasingly blogified as
  "how we operate X" posts.
- **Book-length**: O'Reilly-style trade books, self-published engineer books (e.g. "The Pragmatic
  Programmer" tier), and the serialized-book blog strategy.
- **Talk transcript / conference talk**: increasingly published as essays; the essay-shaped talk
  transcript is its own form.

## 8. Interactive & non-prose forms (the boundary cases)

- **Interactive explainer**: scrollytelling, embedded simulations (Bartosz Ciechanowski, Neal.fun
  lineage). The essay with a physics engine inside.
- **Notebook-style writing**: Jupyter/Observable posts — prose interleaved with runnable code and
  live output; dominant in data science writing.
- **Literate-programming posts**: the article *is* the codebase, lightly.
- **Visual essay / diagram-first post**: the article is the diagram sequence; prose is annotation.
- **Cheatsheet / reference card**: compressed reference, one page, no narrative.
- **Video essay / livestream coding**: not prose, but competes for the same reader attention; blog
  posts increasingly ship with a companion video.

## What the skill's 8 types map to, and the gaps

| Skill type | Covers in the fuller map |
|------------|--------------------------|
| Bug Hunt | Debugging walkthroughs, micro-posts |
| We Rewrote It in X | Migration stories, failed-experiment writeups |
| How We Built It | Engineering-blog posts, trade studies |
| Lessons Learned | Retrospectives, "N years of X" |
| Thoughts on Trends | Essays, rants, analysis |
| Benchmark | Shootouts, performance deep dives (partially) |
| Tutorial | Tutorials, how-tos, recipes, setup guides |
| Explainer | Explainers, internals posts, paper explainers |

Notable gaps the enumeration misses: **postmortems** (mentioned in the skill's description but
given no template — arguably the most conventionalized genre in the industry), **internals /
under-the-hood series**, **"X from scratch" build-alongs**, **release notes / launch posts**,
**concept histories**, and **X vs Y conceptual comparisons**. The intake question "which content
type fits?" should offer this wider menu, or at least allow "none of these — here's the shape" as
a first-class answer.

## Cross-cutting forms (modes, not types)

These attach to any of the types above and are worth naming separately because they're the
structural decision the skill calls "one dominant type plus supporting modes":

- **Series**: any of the above split into numbered installments (internals series, build-along
  series). Changes the hook strategy — each part must hook and close its own loop.
- **Interview/Q&A**: transcript-shaped; common in community and career writing.
- **Annotated code/diff**: the body is a walk through a real diff or file, top to bottom.
- **Live narrative**: "I'm trying X for the first time, writing as I go" — low polish, high
  authenticity, works because the reader shares the uncertainty.
- **Roundup**: N related items under one theme ("5 things I learned from the Postgres source").
